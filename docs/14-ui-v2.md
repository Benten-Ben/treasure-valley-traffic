# 14. UI v2: one map, every layer

The owner asked for a rebuild on Oct 6, 2026: a single map styled like a
city-builder (Cities: Skylines), where every layer can be switched on
together, with 3D buses, stops and cameras, live camera images, buses
replayed along their paths, and a much smoother app. A first draft of this
chapter went through nine specialist reviews the same day: game UI,
cartography and color, transit algorithms, 3D rendering, cameras and
calibration, performance, front-end architecture, lanes, and a red-team
review of scope and risk. The reviewers measured the app, the data and the
libraries. This is the final plan built from those reviews.

- [Chapter 13](13-visual-design.md) still holds the tokens, fonts and
  game-card look. §14.12 lists the changes this plan makes to it, which
  wait for the owner's OK.
- Decisions go in [DECISIONS.md](DECISIONS.md) once the owner answers
  §14.14. Every "Qn" in this chapter is **pending** until then.
- Work is split into packages sized for one agent each (§14.10), with a
  verification plan (§14.11). The questions go to the owner before any
  package is dispatched, and §14.10's gate table says which package waits for
  which answer.

Measurements quoted here come from the Oct 6 reviews. They ran headless
Chromium (SwiftShader, so timings are inflated but bytes and request counts
are not), a production build under `vite preview`, the local PostGIS copy and
`data/tiles`. WP0 re-measures them with one committed script.

## 14.1 Goals and non-goals

**Goals**, in the owner's words where possible:

1. **One map that shows everything.** Layers switch on and off together; the
   map is created once per visit and the view is never lost (calibrating and
   going back used to reset it).
2. **City-builder style:** round info-view buttons, game-card panels, toy-like
   3D buses, bus stops and cameras on poles.
3. **Transit:** more route colors with a measured "too similar" rule, routes
   that share a street drawn side by side, inactive routes visibly muted, and
   buses animated along their GPS path about 90 s behind live.
4. **Streets:** speeds as distinct shades of one blue, without clashing with
   route colors.
5. **Cameras:** each camera's pole, height, heading, tilt and view cone in 3D;
   floating windows with the live image; "look through", which puts the map's
   own camera at the camera's pose so the picture lines up; uncalibrated
   cameras open at ACHD's point with a Configure button; calibration on the
   same map.
6. **Live images:** recorded cameras update by themselves; any camera being
   looked at, looked through or configured updates too.
7. **Smooth:** a measured performance sweep (first load, layer toggles, mode
   changes, animation).

**Non-goals for this round** (designed or noted, built later; §14.13):

- **Lanes** (next round; §14.7 has the design).
- **Full replay** (time bar, 60x and 600x, scrubbing), the camera wall, the
  Valley Feed, search, coach marks (next round).
- **deck.gl and glTF model files.** §14.8 explains why.
- **Agents never touch the server.** Everything is built and verified
  locally; the lead deploys at the checkpoints with the runbook. (The server
  is reachable over the tailnet, and HTTPS with HTTP/2 has been live since
  Oct 6.)

The full list of what's deferred, with checkboxes, is
[DEFERRED.md](DEFERRED.md).

**Added to this round by the owner's answers (Oct 6):** the Road weather
layer (WP16), with its stations loaded from the private 511 list, and a
terrain re-encode (WP17) that makes the terrain file 45–60% smaller.

The owner approved the stepped speed ramp (Q2) and this scope (Q9) on
Oct 6, and the DECISIONS row was corrected to match.

## 14.2 What the reviews changed

Where reviewers disagreed, the table says which way the plan goes and why.

| Topic | Draft | Final plan | Why |
|---|---|---|---|
| 3D engine | deck.gl, "already in the stack" | **Our own small WebGL2 MapLibre custom layer** (`#lib/scene`, about 30–40 KB gzip, lazy), plus a tiny always-loaded 2D overlay for far-zoom buses and badges; three.js as the fallback (Q1) | deck.gl isn't installed. In a headless test, @deck.gl/mapbox 9.4 crashed on MapLibre 6.12, which removed `map.transform`: every frame in interleaved mode, and on `addControl` with terrain in both modes. With a shim it ignores the map's field of view and roll, so look-through misaligns by 10–35 px, and it costs about 340 KB gzip. The cameras reviewer proposed patching deck's view; the 3D and performance reviewers' measurements settle it. |
| Side-by-side routes | deck.gl ribbons | **MapLibre line layers with data-driven `line-offset`** | All reviewers agreed. They drape on the terrain for free, sit under the labels, are hit-tested per slot, and render correctly in 6.12 (prototype screenshots). |
| What "sharing a street" means | Not specified | **A corridor graph built from VRT's own shapes** (transit reviewer), not ACHD centerlines (cartography reviewer) | ACHD covers Ada County only: its centerlines cover just 65–68% of routes 40 and 42, which run into Canyon County. The shape-based prototype builds in 1 s and handles divided roads. |
| Inactive routes | About 30% opacity | **A solid pale "ghost" color, 60% width, slot kept** (cartography and transit), not opacity (game UI, 0.45) | Opacity blends with whatever is underneath: a faded yellow over a blue street reads green, and yellow and lime vanish at 30–40%. A ghost color fades every route evenly, and a kept slot means bundles never reflow. |

| Clay look | One clay switch | **Two basemap flavors, Valley and Clay, switched by paint diff**, replacing both "wash" layers | Today's two washes (0.42 and 0.5) stack, muddy the hillshade, and leave the base as stock Protomaps gray rather than ch. 13's sand. Flavors give a stable background for the color checks. One shared wash (game UI, front end) was the simpler option, but it doesn't fix the look. |
| Palette | "12 or more" | **13 fixed, append-only slots**, a measured separation rule in OKLab with colorblind simulation | Only 5 more hues fit the validator's lightness and chroma limits while staying clear of the UI colors and the streets blue; a 14th would be a near-duplicate. | "The next fix is always known" | Assumed | **Never extrapolate:** a bus waits at its newest fix | Fix to database: p95 62 s, max 68 s, plus the poll. 90 s covers about 99% of steps; 60 s only about 70%. |

A one-hue ramp can't keep ten continuous values apart, so the stops are validated steps. A blend along a road isn't possible on vector tiles (`line-gradient` needs GeoJSON with line metrics). |
| Stops | 3D shelters at every stop | **A 3D sign post at every stop**; shelters only where data says one exists (later) | Most VRT stops are a sign, and ch. 13 says "honest data first". |

| Look-through image | "Fades in over the map" | **The image drawn as a plane inside the camera's view cone in the scene layer**; terrain at true scale while looking | The same plane is the floating "photo in the cone" seen from other angles (game UI and 3D reviewers both proposed it), so one mechanism answers the owner's "floating windows you can look through". ### Layers and the toolbar

**Layers in this round:** Transit, Streets, Cameras. A button appears only
when its layer exists; Lanes and Road weather arrive as further buttons when
built (§14.13). Any combination can be on. A layer's data loads the first
time it's switched on (or is prefetched once the map is idle) and then stays
loaded; turning it off only hides it.

**Buttons:** 52 px round, Phosphor duotone icons bundled with the app
(`phosphor-svelte`, deep imports). Each button shows its label under it on
hover or focus, and always at 1280 px or wider.

| State | Look |
|---|---|
| off | panel background |
| on | pressed in (moved down 2 px), ink background, cream icon |
| keyboard focus | 2 px ink ring inside a 3 px amber ring (amber alone on cream is 2.05:1, below the 3:1 minimum) |
| loading | a rotating ring segment and `aria-busy`; a static dashed ring under reduced motion |
| error | a ▲ badge; the tooltip gives the reason; the legend row offers Retry |

**Tooltip:** name, key, one line on what it shows, and source and age;
after 400 ms, then instant when moving between buttons within 1 s.

**Defaults and memory:** a first visit opens with Transit and Cameras on and
Base on Auto. The layer set and view are saved in `localStorage` (keys under
`tvt:v2:`, every access in try/catch) and in the URL hash. Precedence: URL,
then saved, then defaults. The old `tvt-lens` value migrates once into a
one-layer set.

**Legends** stack in the left column. The most recently turned-on layer's
legend is expanded; the others collapse to one-line rows that expand on
click.

### The color budget

This replaces ch. 13's "at most one data story in color at a time" now that
layers combine:

- **Categorical hue belongs to Transit** (route colors).
- **Streets** use the blue speed ramp when Transit is off, and a pale slate
  version of it (same order, low chroma, 70% width) when Transit is on. Every
  route color then sits at least ΔE 11 from every street shade (15 or more
  for 9 of the 13). The legend shows whichever ramp is drawn and says
  "dimmed while Transit is on; speeds approximate" (the slate steps above
  55 mph are only ΔE 1–2 apart).
- **Ghosts are told from streets by form, not color.** Ghost colors are pale,
  and some sit right on the slate ramp: ghost blue is ΔE 1.0 from slate
  25 mph, violet 3.1, plum 4.6, lavender 5.1. Ghosts are also only 2–4 apart
  from each other (orange/red 2.0, aqua/green 2.3). So every corridor keeps
  its ink outline and cream underlay (§14.4) whether or not its routes are
  running, streets never get that outline, and every ghost ribbon's shield
  names its route. The budget check reports the ghost-vs-street and
  ghost-vs-ghost distances but doesn't require them. The `layers` spec
  checks that the outline is drawn wherever ribbons are, including while a
  route is spotlit.
- **Teal** (`--accent-2`) is for cameras only: view footprints, cones and
  calibrated heads.
- **Amber** (`--accent`) is UI interaction and the "needs calibration" state.
  On the map, selection never relies on amber, since route yellow is ΔE 1
  from it.
- **Magenta** (`--alert`) marks problems and always comes with an icon.
- Lanes, road weather and selection use form, icons and ink/cream only.
- **Status is never color alone:** every status has a shape and a word (●
  live, ▲ late or stale, ■ offline, ◌ not calibrated), the same vocabulary as
  the calibrator's markers. Status text is set in ink with a colored icon
  (teal and magenta text are below 4.5:1 at 13 px).

### Base

The Base button opens a popover:

- **Look:** Auto · Map · Clay. Auto means Clay whenever any data layer is on.
  Switching is a 350 ms paint crossfade (instant under reduced motion).
- **Aerial** on or off (the NAIP imagery; its sources are added only the
  first time it's turned on).
- **Buildings** on or off; **Terrain** on or off; **Labels** full or fewer.

The flavors are in §14.5.

### Top bar, clock and time pill

- **Clock:** the *playhead* time, the moment the buses on the map are at,
  as `5:41:20 PM · Tue` in Overpass Mono.
- **Time pill** beside it:
  - `LIVE −1:30` (filled) at the normal delay; a click opens a popover with
    the delay (1, 1.5, 2, 3 or 5 min; 1 min says "buses may pause"), Pause and
    Go live;
  - `PAUSED −3:05` while paused (data keeps buffering);
  - `LIVE · no new GPS for 3 min` with a hollow dot when the feed stalls;
  - `REPLAY` later, with the time bar.
- **Chips:** `38 buses` · `14/20 routes running` · `34 recording · 11
  calibrated`.
  - Hovering a chip shows its source and age; a click turns its layer on.
  - A chip shows `—` while loading and ▲ when its feed is 2 minutes old or
    more.
  - `aria-live="polite"` announces only threshold crossings.

### Hover, selection and picking

- **One picker** for the whole map. It first hit-tests the overlay's sprites
  and the 3D scene (minimum radius 14 px for the mouse, 22 px for touch),
  then MapLibre features in a
  ±6 px box (±12 px on touch). Priority: bus > camera > hub > stop > route >
  lane > street. Exactly one thing is selected at a time.
- **Shared streets:** a click where several routes share a street lists them
  all ("3 routes here: 7 · 8 · 9"), each opening its route card.
- **Hover:** lines widen 2 px through feature-state; 3D objects get a cream
  tint. A tooltip appears after 200 ms, 12 px from the cursor and flipping at
  the edges, with the name, one fact, and source and age.
- **Selection:** a 2 px ink line with a 3 px cream halo, 1.3× width for
  routes; 3D objects lift 2 m, scale 1.2× and get an ink-and-cream ground
  ring; one 1.2 s pulse (none under reduced motion). Selecting a route
  *spotlights* it: every other route takes its ghost color.
- **Follow:** the bus card has Follow. The view tracks the bus; any drag
  ends it; a banner says "Following bus 2213 · Esc".
- **View history:** every programmatic fly pushes the previous view (10
  deep). A "↩ Back to previous view" chip shows for 8 s, and Backspace pops
  the stack.

### Modes and the view stack

The map is in one of three modes:

| Mode | Owns | Enter | Leave |
|---|---|---|---|
| Explore | default clicks and cursor | — | — |
| Look-through | camera limits, terrain scale, gestures (fade on move) | "Look through" in a camera window | Esc, Step out, or moving far enough that the image fades out |
| Calibrate | clicks (crosshair), base, layer visibility, padding | Calibrate/Configure in a window, or `/calibrate/[id]` | Save, Cancel, Esc or browser Back (the draft is kept) |

Entering a mode pushes a snapshot onto the view stack, and leaving pops and
restores it exactly. The snapshot holds: centre, zoom, bearing, pitch, roll,
field of view, padding, `maxZoom`, `maxPitch`, `centerClampedToGround`,
terrain exaggeration, aerial, look, layer visibility and open windows. Every
map click handler checks the current mode, so a calibration click never
selects a bus.

### Keymap

One registry (`#lib/ui/keys.ts`, WP2) drives both the key handler and the
help overlay. Packages register their own keys from their own modules
(Backspace from WP3, Space and L from WP8, ← and → from WP13), so only WP2
edits the file. Keys are ignored while focus is in an input, textarea,
select or contenteditable element, or while Ctrl, Meta or Alt is held.
Space and Enter are also ignored when focus is on a button, link, summary,
slider or anything with `role=button`, so one press never both activates a
control and pauses playback. Keys are matched by `event.code`, so
Shift+digit works on any keyboard layout. MapLibre keeps its own arrows
(pan), +/− (zoom) and Shift+arrows.

| Keys | Action |
|---|---|
| 2 / 4 / 7 | Toggle Streets / Transit / Cameras (ch. 13's numbers, now toggles; 8 Lanes and 9 Road weather reserved) |
| Shift+2/4/7 | Solo that layer; again to restore |
| 1 | All data layers off; again to restore |
| W A S D | Pan |
| Q / E | Rotate 15° left / right |
| R / F | Tilt up / down 10° |
| H | Home: over Meridian, pitch 50, bearing −12 |
| O | Overview: the whole valley, looking straight down |
| Backspace | Previous view |
| Space | Pause / play |
| L | Back to live |
| ? | Help |
| ← / → | In look-through: next or previous calibrated camera by distance |

`[` `]` (speed), C (camera wall), N (Valley Feed, moved from F) and /
(search) are reserved for later features.

**Esc closes, in order:** help or a popover; the focused window;
look-through; calibrate (the draft is kept); follow; the inspect card; the
selection.

When the toolbar has focus, ← and → move between its buttons (roving
tabindex).

### Loading, errors and honesty

- The shell (top bar and toolbar) paints before the map. A "Building the
  valley…" card lists real steps (style, terrain, each enabled layer with
  counts) and fades on the map's first `idle`. It never blocks input after
  the style has loaded.
- Each legend, the inspect card, each window and the calibrator sits in its
  own `<svelte:boundary>` with a "This panel failed: reload it" fallback.
  Map source errors go to their layer's status (▲ on its button).
  `webglcontextlost` shows a "Map paused" card.
- When a new version is deployed, a toast says "New version: reload when
  convenient" (SvelteKit's version polling every 5 min). A failed lazy chunk
  sets its layer to "Reload to enable".
- Interpolated, guessed or estimated things say so: "between reported
  positions", "route guessed from its path", "location ±25 m (ACHD)", "seen
  0:42 ago".

### Motion and accessibility

- Under `prefers-reduced-motion`: flights become jumps, clay switches
  instantly, nothing pulses or bounces, loading rings are static. Buses
  still move (that's data).
- All text at least 4.5:1, non-text indicators at least 3:1.
- **The badge rule** (bus plates, route shields, legend and card badges):
  - Numerals are at least 14 px bold in the slot's badge text color. That is
    still small text under WCAG (bold counts as large only from 18.66 px), so
    4.5:1 applies.
  - Ten slots reach 4.5:1 plain (§14.4's table).
  - Blue (white, 4.42:1), orange (ink, 4.43:1), red (white, 3.95:1) and the
    unknown-route gray (ink, 3.86:1) fall short. Their numerals get a 2 px
    halo in the opposite tone: ink around white, cream around ink. The halo
    fills the digits' counters, and WCAG's Understanding 1.4.3 treats a halo
    like that as the background, so the measured pair is numeral against
    halo (about 14:1).
  - Contrast is never fixed by changing a palette hex. Slots are fixed and
    append-only (§14.4).
- Camera windows are non-modal dialogs; focus moves in on open and back on
  close. "Dock left" and "Dock right" buttons give a way to place them
  without dragging (WCAG 2.5.7).

Unknown-route buses stay `#8a857c` (ink 3.86, **halo**). "Halo" follows the
badge rule in §14.3. Ink is `#2B2A33`. The palette passes the dataviz
validator's lightness-band, chroma, colorblind and normal-vision checks
against the clay surface. Six slots are under 3:1 contrast, so every ribbon
needs its casing and every route keeps a numbered badge; neither is
optional.

**"Too similar" is a number** (`ingest/route_colors.py`, standard library;
OKLab ×100, Machado 2009 simulation at full severity):

```python
def separation(a, b):
    """1.0 = exactly at the bar: normal-vision ΔE 15, colorblind ΔE 8."""
    return min(delta_e(a, b) / 15, min(delta_e(a, b, "protan"), delta_e(a, b, "deutan")) / 8)

def clash(a, b):
    return a == b or separation(a, b) < 1.0
```

On the 13 slots this gives 12 clashing pairs of 78: blue/plum, orange/yellow,
orange/pink, orange/green, orange/red, aqua/pink, aqua/red, aqua/lime,
yellow/lime, pink/red, green/red and green/brown. It replaces the hand-made
`CONFUSABLE` list, which only covered the fail band and missed 3 pairs, two
of them on live neighbor routes today (10/16 red/green, 28/29 red/aqua).

**Neighbors** (must not clash): routes sharing at least 300 m within 40 m of
each other outside the hubs (today's rule), **or** sitting in adjacent ribbon
slots for at least 100 m anywhere (new, from the corridor graph).

**Sequence.** Slot order and colors depend on each other, so a build runs in
this fixed order:

1. Build the corridors and a crossing-optimal slot order **without
   colors** (below). The result is deterministic.
2. Derive the neighbors from that order, plus today's proximity rule.
3. Assign colors against those neighbors, in the owner's mode (Q3).
4. Run the color pass. It may only swap routes where the crossing cost is
   unchanged **and** the swap creates no clash under the new adjacency.

The stored neighbor graph is the one after step 4. A route changes color only
when a new neighbor makes it clash. When the shapes and the dormant set are
unchanged, the build is skipped. `--force` on unchanged input reproduces it
byte for byte, and a test checks that it changes 0 colors.

**Assignment priorities:**

1. no clash between neighbors;
2. at most `ceil(routes / 13)` routes per color (2 today);
3. fewest changes from the stored colors;
4. the largest worst-case neighbor separation;
5. then palette order.

The search is DSATUR backtracking that tries each route's current color
first, raising the number of allowed changes from 0. When no assignment fits
the budget, it falls back to minimizing the sum of `max(0, 1 − sep)` over
neighbors.

A dry run prints old → new for the owner. **Which mode runs is the owner's
call (Q3):**

- **a one-time rebalance** (on the old neighbor graph the prototype changed
  5 routes: 5, 16, 29, 42 and R1);
- **the minimal fix** (only clashing routes change; the prototype changed 10
  and 28).

Either way, colors stay stable afterwards: a route changes color only when a
new neighbor makes it clash. An optional `color_pinned` flag lets the owner
lock a route's color.

### Side-by-side ribbons

**Built on the server when the shapes or the dormant set change**
(`ingest/transit_ribbons.py`, standard library). vrt_gtfs runs daily, and
each run calls it. It rebuilds only when the build hash, `sha256(active
shapes, dormant set, parameters)`, differs from the stored one. The rebuild
runs inside a savepoint, so a failure keeps the previous ribbons and logs
the error. By hand: `python3 -m ingest.transit_ribbons [--force]`.

**Corridor graph** (greedy owner-interval aggregation; work in UTM 11N metres):

1. Densify every active shape every 5 m (point, unit tangent, measure).
   Process shapes longest first.
2. Each shape point matches the nearest point of an existing *piece* within
   40 m whose tangent is parallel or antiparallel within 35°. The cost is the
   distance, plus 10 m if it isn't on the previous point's piece.
3. Matched runs shorter than 80 m become unmatched. Unmatched gaps under 40 m
   between runs on the same piece are bridged.
4. Each unmatched run becomes a new piece owned by this shape, anchored at
   its ends to the neighboring pieces.
5. Cut pieces at run ends and anchors, clustering cuts within 20 m, to get
   atomic **segments**, each with the set of routes covering it.
6. Join cuts into nodes, and **overwrite each segment's end vertices with the
   node coordinate** (the prototype had gaps without this).
7. Simplify with Douglas–Peucker at 1.5 m. A segment is a hub segment when
   its midpoint is within 300 m of a stop served by 6 or more routes.

Both directions of a route on a divided road (3–30 m apart for 22–64% of
some routes) become one ribbon.

**Slot order** per segment (routes left to right, looking along the segment's
direction) minimizes crossings by local search:

- **Cost:** at every segment end and every route pair:
  - routes continuing to the same next segment in a different relative order
    cost `W_CROSS` = 4 (1 inside hubs, so unavoidable crossings move into the
    hubs);
  - routes adjacent here but not there cost `W_SEP` = 1;
  - routes turning different ways must be on the side they turn to (left of
    the arrival heading means left), or the pair costs `W_CROSS`.
- **Search:** three deterministic starting orders. Try every permutation for
  n ≤ 6, otherwise single-element moves; sweep until nothing improves (at most
  30 sweeps); keep the best start.
- **Color pass:** step 4 of the sequence above. It separates similar
  colors in adjacent slots without changing the crossing cost and without
  creating a clash.
- Prototype: cost 988 → 517 in about 4 s; at most 11 routes on one street.

**Dormant routes** (no fix at all in 7 days) take no slot and are listed in
the legend as "no buses seen since …" (pending Q3). Routes 30, which was
discontinued Oct 1, and R1 are in the feed with no buses.

- **When the rule applies:** only once the positions table spans 7 days. A
  fresh database marks nothing dormant, and the server's recording, which
  started Oct 5, crosses 7 days on Oct 12.
- **Daily re-check:** the dormant set is part of the build hash, and
  vrt_gtfs's daily run recomputes it. A route that goes quiet loses its slot
  within a day of crossing 7 days. A route that comes back gets a slot the
  day after its first bus.
- **Colors:** a dormant route keeps its stored color, so coming back never
  recolors it. Its former slot neighbors become adjacent, which can recolor
  one of them, but only if they clash (sequence step 3).

**Drawing** (MapLibre, `#lib/layers/transit`): each segment expands into one
feature per route with `rid` (a numeric route index, the source's
`promoteId`), `slot` and `n`.

Per-zoom ribbon width `w`, gap `g` and bundle cap `B`, in px:

| Zoom | w | g | B |
|---|---|---|---|
| 10 | 1.5 | 0 | 6 |
| 12 | 2.25 | 0.5 | 10 |
| 14 | 3.5 | 1 | 18 |
| 16 | 5 | 1.25 | 30 |
| 18 | 7 | 1.5 | 48 |

```ts
// R = the rows of the table above, as [z, w, g, B]
const pitch = (w, g, B) => ['min', w + g, ['/', B, ['get', 'n']]];
'line-offset': ['interpolate', ['linear'], ['zoom'], ...R.flatMap(([z, w, g, B]) =>
  [z, ['*', ['-', ['get', 'slot'], ['/', ['-', ['get', 'n'], 1], 2]], pitch(w, g, B)]])],
'line-width': ['interpolate', ['linear'], ['zoom'], ...R.flatMap(([z, w, g, B]) =>
  [z, ['max', 1, ['*', pitch(w, g, B), w / (w + g),
     ['case', ['boolean', ['feature-state', 'active'], false], 1, 0.6]]]])],
'line-color': ['case', ['boolean', ['feature-state', 'spot'], false], ['get', 'color'],
  ['boolean', ['feature-state', 'dim'], false], ['get', 'ghost'],
  ['boolean', ['feature-state', 'active'], false], ['get', 'color'], ['get', 'ghost']]
```

Positive offsets are to the right of the segment's digitized direction, and
all of a segment's features share its geometry, so a route drawn in the
opposite direction can't land on the wrong side. Dense downtown corridors
become a thin multi-colored "cable" that widens as you zoom in.

**Layers on the corridor**, bottom to top, all with round caps and joins:

1. an outline from the segment features: opaque `#86837F` (ink at 55%
   pre-blended on clay, so overlaps at nodes don't darken), width
   `n·pitch + 4.5`;
2. a cream `#FFFBF4` underlay, width `n·pitch + 2.5`;
3. the ribbons.

The cream underlay is required: without it, lime and yellow vanish on parks
and water (contrast 1.3–1.8).

**Hubs:** a station pill (Main Street Station, Towne Square Mall) covers the
knot of lines from z14.

**Route shields:** per-route line labels can't follow `line-offset`, so each
segment gets one label point. Its `text-field` is a `format` expression of
image sections, canvas-made route badges in slot order (ghost badges for
inactive routes), from z13, spacing about 400 px. The shield source is
rebuilt only when the set of running routes changes.

**Ribbon tests** (synthetic, in metres):

- a Y-junction where A goes left and B goes right orders the trunk [A, B]
  with 0 crossings;
- antiparallel lines 25 m apart merge, 60 m apart don't;
- crossing streets don't merge;
- an overlap under 80 m doesn't merge;
- a 30 m detour inside a shared run is bridged;
- a loop closes on one node;
- the same input gives byte-identical output;
- each route's segments cover at least 99% of its shapes;
- consecutive segment ends are at most 1 m apart;
- rebuilding with unchanged shapes and dormant set changes 0 colors and gives
  byte-identical ribbons;
- adding a dormant route to the set changes the hash, and removing it
  restores the earlier build.

**No build yet:** until the first ribbon build exists (a fresh deploy, or a
failed first build), `/api/transit/network` serves each route's plain shapes

On real data: build ≤ 30 s, cost ≤ 520, and routes 40, 42 and 45 share

### Running and not-running routes

- **Running** at playhead time T means some fix attributed to the route (the
  feed's own route, the trip ID's, `trip_route_match` or a provisional path
  match) has a timestamp in [T − 15 min, T]. Buses with no route never make a
  route running.
- The client can decide this exactly from the tracks API's `routeRuns`. For
  each route, it lists spans of fixes over the last 75 min, split wherever
  two consecutive fixes are more than 15 min apart. A route is running at T
  if and only if some span starts at or before T and ends at or after
  T − 900 s. A route's newest fix lying after the playhead doesn't hide
  whether it also had one in the window.
- Not-running routes keep their slot and draw in their **ghost color** (an
  OKLab mix toward the surface, chosen so each ghost sits about ΔE 14 from
  it) at 60% width. The switch is feature-state on the route id, with no
  `setData`.
- The legend has two groups, "Running now (n buses)" and "Not running now",
  and the key line says "Faded: no bus in the last 15 min" in words. When no
  bus reports at all, a chip says "No buses reporting · last fix 11:52 PM".
- Stop capsules where no serving route is running draw at 45%.

### Playback

**Delay:** D defaults to 90 s (owner OK, Oct 6). The picker offers 1, 1.5,
2, 3 and 5 min. Measured from fix to database: p50 37 s, p95 62 s, max 68 s,
plus up to 10 s of client poll.

**Online matcher** (`ingest/transit_progress.py`, standard library), called
by the transit stream after every stored batch of positions. By hand:
`python3 -m ingest.transit_progress --hours N` (it's idempotent: it processes
fixes with no progress row, per vehicle in time order).

**It can never cost us bus positions**, the most valuable live data. It
follows the existing `transit_match` pattern in `vrt_realtime.py`:

- The positions batch is committed first.
- The matcher runs inside try/except. On any error it rolls back, logs, and
  carries on.
- Each call has a time budget of 5 s. Fixes it doesn't reach wait for the
  next batch.
- Runs are serialised with a session advisory lock. The stream uses
  `pg_try_advisory_lock` and skips matching for that batch if the lock is
  held. The backfill CLI takes the same lock and waits for it.
- Rows are written with `on conflict (vehicle_id, ts) do nothing`.
- A fix older than its vehicle's newest progress row is stored with no step
  (`method = 'late'`) rather than re-threading the chain.

- **Candidates:** the shapes of the resolved route (feed, trip ID or
  `trip_route_match`); with no route, every shape within 40 m. The trip ID's
  shape is a hint at most.
- **Projection:** windowed around the previous measure, within
  `[m_prev − 60, m_prev + 30 m/s·dt + 60]`. Loops (ends under 50 m apart)
  wrap.
- **Choice** among projections within 40 m. The cost is the distance, plus:
  - 50 if the bus is moving (12 m or more since the last fix) and the feed
    bearing is more than 60° from the shape tangent;
  - 25 for switching shape;
  - any backward motion beyond 20 m.
- **Steps** between consecutive fixes (dt, chord c, Δm along the shape):

| Kind | Rule | Speed |
|---|---|---|
| gap | dt > 150 s | — |
| still | c < 12 m, or −20 ≤ Δm < 0 | 0 |
| along | same shape, 0 ≤ Δm ≤ 3c + 100, Δm/dt ≤ 30 m/s | Δm/dt |
| straight | anything else, including off every shape | c/dt |

- **Provisional route:** when the route is unknown and the last 4 "along"
  fixes are each within 40 m of exactly one route's shapes, it sets
  `route_source = 'path'`. `trip_route_match` wins when it exists. This cuts
  the 5–10 minutes an unlabeled bus stays gray today.
- **Prototype**, on 432 local fixes: 232 along, 71 still, 14 gap and 6
  straight for labeled buses; p99 matched distance 14.5 m.

**Tracks API** (`GET /api/transit/tracks?window=120`, at most 900 s; a past
`at=<ISO time>` pins the window for replay and tests):

- One query joins positions with progress and the next fix (`lead()`).
- "Along" steps carry their path, a `ST_LineSubstring` of the shape between
  the two measures (two pieces across a loop seam).
- Fixes with no progress row yet still come through, as `straight` steps
  between fixes. That covers the time before the backfill, or the matcher
  running behind. Playback never goes blank.
- A 5 s in-process micro-cache means N viewers cost one query.

```ts
{ now: number;                                   // server time, epoch s
  vehicles: Record<string, { label; routeId; routeSource; shortName; color; textColor; halo; headsign }>;
  steps: [vid: string, t0: number, t1: number | null, kind: 'along' | 'still' | 'straight' | 'gap' | null,
          lon0: number, lat0: number, bearing: number | null, speed: number | null,
          path: number[] | null][];              // flat lon,lat,… including endpoints
  routeRuns: Record<string, [start: number, end: number][]>;  // fix spans per route, last 75 min,
                                                 // split at gaps over 15 min (see "Running")
  lastFix: number | null }                       // newest fix of any bus, any age ("No buses reporting")
```

A bus's newest fix arrives as a step with `t1 = null`, and a later poll
replaces it (keyed by vehicle and `t0`). Expect about 4–8 KB gzip per poll.

**Client** (`#lib/layers/transit/playback.ts`, pure and unit-tested):

- **Clock:** offset = median over the last 5 polls of
  `server now − (send + receive)/2`. Playhead `T = Date.now()/1000 + offset −
  D`, or a pinned `at`.
- **Feed:** polls every 10 s while the tab is visible (initial window
  `D + 360 s`, capped at 900), merges by key, and prunes steps older than
  T − 6 min. When the tab becomes visible again it reloads the window and
  jumps.
- **`positionAt(steps, T)`:**

| Step | Position |
|---|---|
| along | constant speed along the step path between t0 and t1 |
| straight | linear between the fixes |
| still | at the fix |
| gap | holds, then a 300 ms fade-jump |
| newest fix reached (`t1` null or T ≥ t1) | waits at the fix, never extrapolates: "waiting for GPS" under 120 s, hollow (stale) up to 15 min, then hidden |

- **Heading:** the path tangent over ±8 m, low-passed with τ = 300 ms; the
  feed bearing only for a first fix or a still step.
- **Trails:** off by default. When on, an ink 1.5 px breadcrumb along the step
  paths over the last 5 minutes, a draped line source updated at most once
  a second. It's the one named exception to the "once per poll" rule in
  §14.8.
- Buses are drawn at their true position, not on their ribbon slot.

**Tests:**

- an out-and-back shape keeps the right pass;
- on overlapping opposite shapes, the bearing picks the direction and
  progress stays monotonic;
- a loop seam gives one along step;
- off-shape → straight; 200 s → gap; 8 m jitter → still; a 40 m/s step →
  straight;
- `positionAt` at t0, mid-step and t1, and the waiting, stale and hidden
  transitions;
- a ±60 s clock offset doesn't change positions.

**Acceptance in the build session**, on the 17 local minutes (432 fixes,
Oct 5, 20:17–20:34 UTC, replayed with `at=`):

- 90% or more of labeled-bus steps are along or still (the prototype got
  94%);
- no along step faster than 30 m/s;
- no backward motion over 20 m;
- under 2 ms of playback math per frame for 42 buses (synthetic load).

**Acceptance after deploy**, on a recorded weekday hour on the server
(runbook step 6): the same four checks, plus under 2% of bus-seconds waiting
at D = 90.

- **The waiting share** needs each fix's arrival time. Migration 0007 adds
  `seen_at` to progress rows. The online matcher writes it right after each
  stored batch, so it marks arrival to within the 5 s budget. Backfilled
  rows are left out of this check.
- **Running the hour-long checks locally:** there's no such hour in the
  build session. If the helper or the owner provides an hour of positions as
  a local fixture, the other hour-long checks can run there too. That
  fixture is VRT data, CC BY 3.0 and credited, and is kept in git-ignored
  `data/`.

### Live images

**Where frames come from:**

| Camera | Source | Refresh |
|---|---|---|
| Recorded key cameras | the capture archive's newest frame | every 50 s (capture); never fetched from 511 by the app |
| Road-weather views | the capture archive's newest frame | every 10 min (capture); once these views are in the database (Q8), open ones may also refresh from 511 within the caps below |
| Everything else | 511's republished image, fetched by the server only while someone has it open, looked through or in calibration | at most once per 55 s per image |

**Server (`#lib/server/archive.ts`, `live511.ts`, `robots.ts`):**

- **Archive mount:** the app container mounts only
  `${ARCHIVE_DIR}/cameras/jpeg`, read-only (pending Q5).
- **Newest frame:** the tail of today's `index.csv` for that image (falling
  back to yesterday's), read only when the file's size or modification time
  changes; nothing else is read for unchanged views.
- **511 fetcher**, single-flight and in memory:
  - only view IDs in `core.camera_view`;
  - each image at most once per 55 s, and concurrent callers share one fetch;
  - at most 2 upstream requests at a time;
  - at most 12 distinct on-demand images per 10 minutes;
  - refreshing stops 3 minutes after the last client asked.
- **robots.txt:** checked through a port of `ingest/http.py`'s lenient RFC
  9309 parser, with the same test cases, cached 24 h. A 5xx or network error
  means "blocked" for now.
- **Identity:** the same User-Agent as the ingestors (a test compares the
  two).
- **Storage:** frames are kept in an LRU of 64, in memory only. Nothing is
  written to `FRAMES_DIR` unless a frame is chosen for calibration.
- **Status file:** the capture services also write
  `cameras/status/<tag>.json` each cycle (cadence, image IDs, heartbeat,
  paused-for-low-disk), mounted read-only, so the app knows what's recorded
  and whether capture is alive (pending Q5).
- **Switch:** `CAMERA_IMAGES_ENABLED` turns all of this on or off. It
  defaults to off in code. Compose turns it on for the tailnet deployment
  only once Q5 is answered yes, and it can be turned off again if the site
  is ever opened more widely.
- **Fixture mode:** `TVT_FRAME_SOURCE=fixture` serves seeded frames instead
  of fetching, so tests and agents never reach 511. WP0 adds this switch to
  today's `frames.ts` (the calibrator's frame capture), and WP11 extends it
  to the new fetcher.

**Endpoints:** `GET /api/cameras/live`, `GET /camera-frames/…`,
`GET /api/views/[id]/live/[sha]` and `GET /api/cameras/status` (§14.8).

**Client:** one batched poll of `/api/cameras/live` every 15 s while any
window, look-through or calibration is open (every 60 s if all of them are
slow-cadence views), paused while the tab is hidden.

**Freshness:** age is "seen" time, when our server first got that picture
(repeats are dropped). The tooltip says the time printed under the picture is
ACHD's own clock. Until that time is read automatically (deferred), the UI
says "seen", never "taken".

| Cadence | ● fresh | ▲ late | ■ stale | ◌ |
|---|---|---|---|---|
| Key cameras and 511 on demand | ≤ 3 min | ≤ 10 min | > 10 min | no frame yet |
| Road-weather views | ≤ 30 min | ≤ 60 min | > 60 min | no frame yet |

"Blocked" reads "robots.txt doesn't allow it right now". A thin ring around
the dot fills over the cadence and pulses when a new frame arrives.

### The photo in the cone

For each open window of a calibrated camera, from z15, the live image hangs
as a framed quad inside the view cone:

- **Placement:** perpendicular to the view axis, sized to about 140 px wide
  on screen. Corners are `apex + d·(forward ± tx·right ± ty·down)`, with
  `tx = tan(vfov/2)·W/H` and `ty = tan(vfov/2)`.
- **Faces:** the front shows the photo, with the burned-in 511 bar cropped;
  the back is a cream panel with the camera's name.
- **Texture memory:** an LRU of at most 16 textures (about 30 MB).

It reads correctly from any angle as a picture in the right place and
direction, which is the owner's "floating windows you can look through".
Because it lies on the frustum, flying the map camera to the apex makes it
fill the view exactly; look-through is a continuous zoom into the window.

The ground drape (today's "Camera images on the map") is removed from the
main map. It stays only inside calibration, as a check.

### Look through

1. **Save** the full view snapshot (§14.3).
2. **Terrain to true scale:** `setTerrain({source: 'terrain', exaggeration: 1})`.
   This is one call that doesn't refetch tiles. Poses are stored in true
   metres while the map draws terrain at 1.3×, so a camera placed naively
   sits about 240 m underground; compensating instead leaves up to 8 px of
   error, against 0.34 px at 1.0 (pending Q6).
3. **Limits:** `setMaxPitch(89)`, `setMaxZoom(24)`, `setPadding(0)`,
   `setCenterClampedToGround(false)`. Explore keeps `maxPitch` 75 (pitch over
   60° is experimental in MapLibre and loads many tiles), and traffic cameras
   need pitch 70–87. Close, steep cameras on tall screens need zoom above
   22.
4. **Fit the image:** the chrome collapses to a slim mode strip. The image is
   letterboxed at its aspect in the canvas, with
   `h_img = min(0.92·H, 0.96·W·h/w)`. The map's vertical field of view becomes
   `Vm = 2·atan(tan(Vc/2)·H/h_img)`, set with `setVerticalFieldOfView`
   **before** computing the camera options (the zoom depends on it).
5. **Place the camera:**
   `calculateCameraOptionsFromCameraLngLatAltRotation([lon, lat], alt, heading, 90 − tilt, roll)`,
   then `jumpTo` with its `elevation`. A second pass sets the elevation to
   the terrain under the computed centre and recomputes, so restoring the
   clamp later doesn't jump.
6. **Fly in** with our own 1.2 s animation-frame loop, interpolating the eye
   position (with a 40 m arc when the flight is longer than 300 m), bearing,
   pitch, roll and field of view. Each frame sets the field of view first,
   then jumps. Under reduced motion, it jumps straight there.
7. **Check:** read back the camera position; it must be within 0.1 m.
   Otherwise show "Can't place the map camera at this pose" and stay out.
8. **Show:** the photo plane moves to `d = max(2 m, 2 × near)` from the
   eye, where `near` is the map's near clipping distance in metres. With
   depth testing off, its size on screen doesn't depend on d. It draws at
   85% opacity, with a 40% ink vignette outside the frame and a 2 px cream
   viewfinder edge. The camera's own model and cone are hidden. The roll
   sign is settled by the registration test, not by reasoning.
   - Why the max: MapLibre 6.12's Mercator transform puts the near plane at
     `height / 50` pixel units. In metres that grows with the eye-to-centre
     distance, so for a low-tilt camera it passes 2 m (about 2.3 m for a
     12 m pole at 5° tilt). A plane at a fixed 2 m would be clipped and the
     picture would vanish.
9. **HUD:**
   - an opacity slider;
   - both clocks ("picture seen 0:48 ago · buses 1:30 behind");
   - ← and → to the next or previous calibrated camera;
   - Step out.
10. **Fade on user moves only:** let D = (alt − ground)/sin(tilt). The
    deviation is
    `e = max(Δangle/4°, |eye shift|/(0.08·D), |Δroll|/3°, |ln(fov ratio)|/0.15)`,
    and opacity = `clamp(1 − e) × slider`. After 300 ms at 0, look-through
    ends where the user is:
    - over 400 ms, pitch eases to 75° or less, zoom to 22 or less, and the
      field of view back to 36.87°;
    - then the limits and the ground clamp are restored, so nothing jumps;
    - then the exaggeration eases back to 1.3, with the camera kept at
      least 10 m above the exaggerated ground, so it never ends up inside a
      hill.

    Esc or Step out flies back to the saved view and restores it exactly.

### Calibrating on the map

`/calibrate/[id]` (with `?view=`) is a child route of the map layout, so it
renders only the calibration panel over the same map. Browser Back leaves,
Forward re-enters, and a reload resumes the draft.

**Entering:**

- The snapshot is saved; aerial goes on, clay off, buildings to 0.25.
- Transit, Streets and other cameras are hidden; this camera's pole and live
  cone stay.
- The map goes to pitch 0, bearing = the solved heading (north if
  uncalibrated), zoom 19, centred on the footprint or the pole. It gets
  there with `jumpTo`, not a flight, so no tiles load for the zooms in
  between. Leaving restores the snapshot with `jumpTo` too.
- Terrain goes to true scale. The calibrator must divide terrain heights by
  the *current* exaggeration, not the manifest's.
- A crosshair cursor; clicks belong to the calibrator.

**Panel** (docked left at 45% width, 900 px screens and wider; the map's
left padding equals the panel width):

- the frozen reference frame (zoom and pan), so pairs refer to one picture;
- a small Live inset and a reference-vs-live blink compare;
- the numbered pairs and the live solve card (height, heading, tilt, field of
  view, each pair's error, RMS);
- **Check alignment**, which runs look-through with the unsaved pose;
- the drape toggle, kept as a check;
- **Use this frame**, which freezes the live picture currently shown (in
  the inset) as the new reference. It persists that picture at once:
  - the client posts its identity: the `sha` of an on-demand 511 frame held
    in memory, or the image, day and stamp of an archive frame;
  - the server copies exactly those bytes into `FRAMES_DIR`;
  - if they're gone (out of the memory cache, or trimmed from the archive),
    it answers 410, and the panel asks to pick the current frame again.

  The pairs are clicked on the frozen frame, so the saved reference is
  always the picture they refer to;
- keys: Ctrl+Z undo, Delete removes the selected pair, Ctrl+S saves.

**Drafts** are saved per view in `localStorage` (`tvt:v2:calib-draft:<viewId>`).

**Leaving:**

- Save posts the calibration, refreshes the camera data, restores the
  snapshot, reopens the window and offers "Look through to check".
- Cancel asks first if the pairs changed.

**Fixes carried into the new calibrator:**

- **Timestamp bar:** its height is now computed per frame: `H − round(W·9/16)`
  when that's between 20 px and 10% of H, else `round(0.073·H)`. The HD I-84
  frames (1920×1166) were draping about 50 px of bar onto the ground with the
  fixed 36 px.
- **The first frame shown** in a new calibration is the newest one: from
  the archive when it holds a frame seen within the last 2 minutes,
  otherwise from the live fetcher. Whatever is shown is what "Use this
  frame" saves.

The old page stays at `/v1/calibrate/[id]` until the owner has saved a
calibration with the new one.

### App context, boot and the view

```ts
interface AppCtx {
  readonly map: Map | null;                // $state.raw
  readonly manifest: BasemapManifest | null;
  readonly status: 'loading' | 'ready' | 'unavailable' | 'error';
  styleReady: Promise<Map>;                // 'style.load', not 'load'
  meta: DataMeta;                          // data versions from /api/meta
  layers: LayerManager; picker: Picker; modes: Modes; view: ViewManager;
  clock: Clock; windows: WindowManager; selection: Selection;
  loop: Loop; overlay: Overlay;            // the always-loaded 2D overlay
  scene(): Promise<Scene>;                 // the 3D mesh engine, loaded on demand
  exaggeration(): number;                  // live terrain exaggeration; the one place 3D code reads it
}
```

**Boot:**

- `boot.ts` runs at module scope, before the map exists. It fetches the
  manifest and `/api/meta` (both preloaded from `app.html`, so they're in
  flight while the JS parses) and calls MapLibre's `prewarm()`.
- Each enabled layer's data fetch starts the moment `/api/meta` resolves,
  since its URL carries a version (`?v=`). The serial step is one tiny
  preloaded response, which keeps the ≤ 300 ms data-start target.
- `/api/meta` (WP0, memoized 15 s) reports the GTFS feed version, the
  ribbon build (or `none`), roads, cameras, calibrations and the tiles'
  build dates. It tolerates tables that don't exist yet (`to_regclass`), so
  it works before and after migrations 0006 and 0007.
- Layers attach on `style.load`, never after the full `load`, and never
  wait on one another.
- Off layers' JSON is prefetched on the first `idle`, so their first toggle
  is instant.

**Map options:**

- `hash: false`, `refreshExpiredTiles: false`;
- the tile cache is sized so that a calibrate or look-through round trip
  finds the original view's tiles still cached. That means MapLibre's
  default `maxTileCacheZoomLevels` (5) or a larger `maxTileCacheSize`, not
  less. WP5's memory soak checks the cost, and any later reduction must
  keep the round-trip spec green;
- `pixelRatio: min(devicePixelRatio, 2)`, `validateStyle` in development
  only;
- the PMTiles protocol with `metadata: false` (attribution comes from the
  manifest).

**View module:**

- **Hash:** it owns `#map=z/lat/lng/bearing/pitch&layers=…`, written on
  `moveend` (debounced 500 ms) through SvelteKit's shallow `goto(…, {shallow,
  replace})`. It's suspended while a mode is active.
- **Legacy links:** an old `#z/lat/lng/…` hash is rewritten once.
- **Deep links:** a calibration link opened fresh has no saved view; leaving
  goes to the camera at z16, pitch 50.

**Modules clean up after themselves:** every source, layer, handler and
marker a module adds is removed in its cleanup. The first calibration adds
the aerial layers, which then stay, hidden. A test checks that the style's
layer ids after round trips 2–5 equal those after round trip 1.

**Debug handle:** `globalThis.__tvt = {map, mapsCreated, ready, layers}`,
read-only, for tests and the console.

### Layer order

MapLibre renders fill, line, raster and hillshade layers into per-tile
textures draped on the terrain; each *contiguous* run of them is one terrain
draw. Today's insertion points would give up to 4 terrain draws per frame
with every layer on. The order is fixed by invisible anchor layers that
`buildStyle` inserts (`#lib/map/order.ts`), and every module inserts before
its own anchor, so the order doesn't depend on which layer loads first.
Bottom to top:

| # | Slot | Contents |
|---|---|---|
| 1 | base | basemap fills and lines (Valley or Clay flavor), rail |
| 2 | hillshade | from the terrain source by default; a capped second source behind a flag until Q7 (WP5 builds both) |
| 3 | aerial | NAIP, NAIP detail (when on) |
| 4 | `anchor:streets` | streets casing, speed alone / under |
| 5 | `anchor:lanes` | lane surfaces and markings (later) |
| 6 | `anchor:footprints` | camera view footprints |
| 7 | `anchor:routes` | corridor outline, cream underlay, ghost and running ribbons, trails |
| — | **end of the single draped block** | |
| 8 | buildings | `buildings-3d` (fill-extrusion) |
| 9 | `scene-3d` | custom 3D layer (lazy): buses, stop posts, camera poles and heads, frusta, photo planes |
| 10 | `anchor:points` | 2D stop capsules, camera icons below z15, hub pills |
| 11 | base labels | thinned in Clay |
| 12 | `anchor:labels` | route shields, speed numbers, one-way chevrons, lane arrows, road-weather badges |
| 13 | `overlay` | custom 2D layer (always loaded): bus discs and number plates, selection rings, window badges |

A pure function `rttStacks(layers)` has a unit test asserting at most one
draped run for every on/off combination of the layers.

### Render loop rules

- **One scheduler** (`#lib/map/loop.ts`) owns continuous rendering. It calls
  `triggerRepaint()` only for running tweens, or when buses are visible and
  enough time has passed for the fastest bus to move about half a pixel
  (target fps = clamp(2 × fastest on-screen speed in px/s, 2, 60)). It stops
  when the tab is hidden or nothing animated is visible.
- **No `setData` inside an animation frame.** Anything that moves every frame
  lives in the overlay or the scene layer (instance buffer updates). Line and
  fill sources change at most once per poll, because any change re-renders
  their draped terrain textures. The one exception is bus trails, when on, at
  most once a second.
- **Paint state, not data:** running, spotlight, hover and selection use
  `setFeatureState`; layer toggles use layout visibility.
- **No Svelte `$state` writes per frame.** The UI reads a 1 Hz clock; large
  arrays are `$state.raw`.
- **Small things:** `getLayersOrder()`, never `getStyle()` (it serializes all
  GeoJSON); no `backdrop-filter` over the canvas; windows move with
  `transform` while dragging.

### The overlay (always loaded)

Buses have to draw at the default view (z10, Transit on) without the 3D
chunk and without `setData`. So the small things that move, or that follow
the camera, live in `#lib/overlay/` (WP2). It's part of the initial bundle:
≤ 12 KB gzip together with the shared `#lib/gl/` helpers.

- **One custom layer,** `overlay` (slot 13), draws screen-aligned sprites
  from one instance buffer: bus discs with their route-number plates,
  selection rings and window number badges.
- **Sprites** come from one atlas texture. Plates and numerals are drawn on
  a canvas once per route, following the badge rule in §14.3.
- **Projection:** each anchor (lon, lat, and elevation from
  `queryTerrainElevation`) is projected on the CPU in float64 with the
  frame's `mainMatrix`, so sprites sit exactly where `map.project` says,
  terrain included.
- **API:** `overlay.set(group, instances)` and, for moving things,
  `overlay.update(group, fn)`, which runs once per rendered frame. Each
  group registers its sprites with the picker (screen centre and radius)
  and asks the loop for frames only while something moves.
- **With models:** from about z15 the 3D engine draws bus models; discs
  fade out as models fade in (over 0.3 zoom), and the plates stay in the
  overlay at every zoom.
- **Error fallback only:** if the overlay can't start (no WebGL2 custom
  layer), buses fall back to a MapLibre symbol layer updated by `setData` at
  most twice a second. The Transit button shows ▲, and the performance
  targets don't apply to this fallback.

### The 3D engine (instead of deck.gl)

| Option | Gzip size | MapLibre 6.12 with terrain | Look-through exact (fov and roll) | Notes |
|---|---|---|---|---|
| deck.gl 9.4 (MapboxOverlay, mesh layers) | about 340 KB (251 KB without glTF) | **no**: crashes; works only with a private-field shim | fov only, by injecting a view; roll impossible | `TerrainExtension` can't follow MapLibre's terrain |
| three.js 0.186 custom layer | about 155 KB | yes | yes | still needs our own precision math and picking |
| **Own WebGL2 custom layer** | **about 30–40 KB** | yes, public API only | **yes: 0.34 px measured** | about 1,000 lines; prototype 0.3 ms of JS per frame at 1,000 instances |

`#lib/scene/` (the mesh engine) is a lazy chunk, loaded with `import()`:

- It's never requested before the map's first `idle`.
- After that idle, it's prefetched if Transit or Cameras is on.
- Otherwise it loads when one of them is turned on.

Models only appear from about z15, so nothing at the default view waits for
it.

**Files:** `index.ts`, `layer.ts` (`scene-3d`, `renderingMode: '3d'`),
`rtc.ts`, `ground.ts`, `pick.ts`, `textures.ts`, `meshes.ts` and
`batches/*`. GL plumbing comes from `#lib/gl/`.

**Projection and precision:**

- Uses MapLibre's own `defaultProjectionData.mainMatrix` from the
  custom-layer render arguments, so it's exact in every camera mode and
  shares the depth buffer with terrain and buildings.
- Renders relative to centre: each frame takes `origin = mercator(map
  centre)` in float64. Instance offsets are float32 metres from it, and
  `u_m = mainMatrix · T(origin) · S(k, −k, k)` is multiplied in float64 and
  cast to float32. Plain float32 mercator jitters 22–45 px at z22, where
  look-through and calibration work.

**Drawing:**

- One instanced draw per mesh type, 12 draw calls or fewer in all. Order:
  opaque models → blob shadows → cones (blended, no depth write) → photo
  planes (front face photo, back face panel).
- **Ground:** `renderedZ(trueZ, groundTrue) = exag·groundTrue + (trueZ −
  groundTrue)`, reading the live exaggeration. Moving objects use
  `queryTerrainElevation`, with z tweened over 200 ms when DEM tiles refine.
- **Lighting:** flat and high-ambient (ambient ≥ 0.7). Tinted faces darken at
  most 12%; the light direction follows the style's light.
- **Picking:** on the CPU. Each instance's screen centre and radius are
  stored during render; hover and click test them within max(radius, 14 px)
  through the central picker, so a click on a 3D bus never also selects the
  route under it.
- **Robustness:** textures upload in `prerender` from `createImageBitmap`.
  GPU resources are rebuilt on `webglcontextrestored`. Antialiasing stays off
  until measured on the owner's laptop.

**Later:** revisit deck.gl only when @deck.gl/mapbox supports MapLibre 6,
and only for heavy analysis layers (hexbins, an all-day trips replay). This
would amend the Oct 5 "MapLibre + deck.gl" decision (pending Q1).

### Schema

Both migrations need the owner's OK (Q4). Until then they live in

create table core.transit_ribbon (
  segment_id int primary key,
  geom geometry(LineString, 4326) not null,  -- shared centreline piece
  routes text[] not null,                     -- left to right, looking along geom
  length_m real not null,
  hub boolean not null default false,
  build text not null);                       -- sha of shapes + parameters
alter table core.transit_route add column color_pinned boolean not null default false;

-- db/migrations/0007_vehicle_progress.sql
create table obs.vehicle_progress (
  vehicle_id text not null, ts timestamptz not null,
  shape_id text, m real, off_m real,          -- null shape: off every shape
  route_id text, route_source text,           -- feed | trip | matched | path
  step text, step_speed_ms real,              -- to the next fix: along | still | straight | gap

About 90k progress rows a day. Each step is written within a minute, so well

### Causes, ranked

1. **Terrain is most of every load.** Two DEM sources fetch 8–13 MB of
   low-zoom PNG tiles: the hillshade source loads full-zoom tiles on top of
   the terrain mesh's half-resolution ones.
2. **Data layers wait for the whole map**, then load one after another.
3. **The map is rebuilt on every page change**, and the back link drops the
   view.
4. **Caching:**
   - pmtiles 4.5 forces `no-store` on Chrome and Edge for Windows, so tile
     cache headers do nothing there;
   - `manifest.json` is cached for an hour;
   - road tiles expire after 10 minutes, and tiles refresh hourly in an
     open tab.
5. **GPU work with everything on:** several draped runs, and per-frame data
   updates that re-render terrain textures.
6. **HTTPS and HTTP/2:** done in Caddy, waiting on Tailscale certificates.
   The tailnet HTTPS address should be the one bookmark: the LAN address has
   its own cache and saved settings.

## 14.10 Work packages

### Rules for every package

- **Isolation:** one git worktree per package on its own branch; one
  database clone (`su postgres -c 'createdb -O tvt -T tvt tvt_<wp>'`, since
  the `tvt` role can't create databases); one fixed dev port (5201 + package
  number).
- **An integration branch, merged after every wave.** The integration
  branch is the session's assigned development branch.
  - When a wave starts, each of its packages branches from the integration
    tip, so it has every earlier wave's code.
  - When the wave's packages are done, a wave integrator merges them in
    dependency order and re-runs every check on the merged tree. It also
    applies any contract change a package asked for. Only then does the next
    wave start.
  - `main` is fast-forwarded at an owner checkpoint, once the checks pass
    and the diff has been checked for private details.
  - Work waiting on a "local only" answer (Gates, below) is inert on `main`:
    - migrations pending Q4 sit in `db/pending/`, which `db/migrate.py`
      doesn't apply. The harness applies them to package clones, and they
      move to `db/migrations/` after the answer;
    - live images stay off: `CAMERA_IMAGES_ENABLED` is unset, and the
      archive mounts live in `deploy/compose.live-images.yml`, an override
      the runbook adds only after Q5;
    - the hillshade look (Q7) is reviewed from screenshots at checkpoint 1,
      before anything is deployed.
- **Data for worktrees.** `data/` is git-ignored, so a fresh worktree has
  none. The harness exports absolute paths into every package's
  environment, with `$MAIN` the main checkout:
  - `TILES_DIR=$MAIN/data/tiles` (read only);
  - `FRAMES_DIR` and `TVT_ARCHIVE`: the package's own copies,
    `$MAIN/data/dev/<wp>/frames` and `$MAIN/data/dev/<wp>/archive`, made
    by `npm run seed` from the seeded templates;
  - `DATABASE_URL` pointing at the package's clone;
  - `TVT_FRAME_SOURCE=fixture`, `CAMERA_IMAGES_ENABLED=true` and
    `TVT_E2E_REQUIRE_DATA=1`.

  With that last flag, a missing manifest, frames directory or archive
  fails the run instead of skipping it.
- **Specs must actually run.** Each hand-back reports how many specs ran,
  passed and were skipped, overall and for its `@wp<n>` tag. The tag's count
  must be above zero with none skipped. A package whose specs didn't run
  isn't done.
- **Ownership:** a package edits only the files it owns (below). A file
  listed under two packages is edited in the order shown in "Shared files";
  new test and spec files belong to whoever creates them.
- **Fixed points:** only WP0 and WP2 edit `app/package.json` and the
  lockfile. Migration numbers are reserved (0006 WP6, 0007 WP7). The JSON
  contracts in `#lib/contracts/` change only through the wave integrator. A
  package that needs a change says so in its hand-back and works against the
  frozen version meanwhile.
- **Never:**
  - fetch from 511. `TVT_FRAME_SOURCE=fixture` exists from WP0 on, and the
    harness sets it for every dev server and spec;
  - touch the server, Tailscale, `deploy/.env` or the private files;
  - commit anything from `data/` or any real camera image;
  - weaken an existing test.
- **Before handing back:**
  ```
  cd app && npm run check && npm test && npm run build && npm run test:e2e -- --grep @<wp>
  python3 -m unittest discover -s ingest/tests -t .
  python3 -m unittest discover tools
  python3 tools/check_public.py
  ```
